Um socket é... ok deixa-me pensar: Um socket é um dispositivo virtual controlado e gerido pelo sistema operacional que serve de abstração usada pela camada aplicacional para permitir estabelecer conexões, enviar packets, etc. Na forma como são implementadas em vários middlewares, como as bibliotecas standard de C e nas de python, um usa-as como apontadores de ficheiros, escrevendo-lhes e lendo-lhes consoante o sistema operacional nos deixa. Bloqueiam, exista uma quantidade limitada de memória que os seus buffers podem conter... tambem gerido pelo sistema operacional, e, consoante o protocolo de comunicação preferido... existem varios tipos: stream driven ou message driven, ponto a ponto ou ponto a multi-ponto, ordenado ou não ordenado, confiavel e não confiavel...
Por exemplo:
Tanto TCP como UDP são ponto a ponto. mas, enquanto TCP garante que a mensagem chega ao outro lado assumindo que uma conexão é estabelecida, o UDP não tem essa garantia, sendo uma forma de enviar blocos de dados sem assoberbar o outro lado com memória.
TCP é usado, por exemplo, para transferir ficheiros em que integridade seja importante e UDP é usado, por exemplo, para transmitir media em direto, por exemplo em live streams.
Não notas que, às vezes, as transmissões caem em qualidade ou ficam menos nitidas por alguns momentos? Isso é devido a quedas na transmissão de pacotes.
E como a tua voz fica deturpada no outro lado quando a conexão é fraca? È porque a transmissão da tua voz, na aplication layer que estás a operar, utiliza UDP para transmitir os dados relativos ao input que metes no microfone.

Sockets são a forma como comunicas com outros computadores. To cria-las, inicializando-as com um endereço na tua maquina correspondente a uma das suas interfaces de rede... tipo WIFI, ethernet, etc. (existem comandos no sistema operativo para descobrir que endereços podes usar. assim como documentação).
Para sockets que são connection driven, como TCP, precisas, não só de a inicializar com um endereço, dando-lhe "bind" a uma interface... mas, se planeias receber conexões usando ditas sockets, precisas de assinalar as suas flags de "listen" e de lhes atribuir um backlog... isto é... a quantidade de conexões que podem manter simultaneamente. Quando aceitas uma conexão com essa, a função que usas devolve-te outro socket... que vai servir, do lado do servidor, como o ponteiro de ficheiro que é de facto usado para transferir os dados. Do lado do cliente... também precisas de establecer um bind... mas como o cliente é que se conecta ao servidor, pelo principio de "se não é vaca, é boi", o cliente não precisa de fazer listen.
Sim. É uma trabalheira. E muitos, muitos, muitos bugs incrivelmente etéreos surgem deste processo. Mas isso é o que define TCP: É como pavimentar uma estrada limpa e suave pela qual as suas mensagens podem passar de forma segura.
Enquanto que com UDP... tu basicamente assumes que existe alguém do outro lado para receber as tuas mensagens e "só mandas memo". Não existe estrada. É como se enviasses as tuas mensagens de catapulta, enquanto que TCP precisa que exista conexão para garantir que a "stream" não se quebre.
